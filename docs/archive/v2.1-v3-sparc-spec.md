## Slice A: LangFuse Deep Integration (v2.1)

### What it does
Completes the LangFuse observability UX to full spec depth. The current implementation has the plumbing (traces write, basic charts render) but lacks the rich interactive features the spec requires.

### Inputs / Outputs
- **Input**: LangFuse trace data from pipeline runs
- **Output**: Rich, interactive Observability dashboard with drill-down, AI insights, and cross-linking

### What's genuinely net-new vs. enhancement

| Area | Current State | Spec Target |
|------|--------------|-------------|
| **Cost chart** | Simple bars (total/day) | Stacked by model, running total line, hover popovers with token counts, click-to-navigate |
| **Latency chart** | Avg bars + p50/p90 lines | Stacked by stage (color-coded per stage), per-model comparison |
| **Quality chart** | Area chart + failure bars | Confidence band, first-try vs retry stacked area, AI insight, cost-vs-quality scatter |
| **Trace metadata** | Stage name + output text | Per-stage: model, tokens_in, tokens_out, cost, latency_ms in trace data |
| **Cross-linking** | onNavigate prop exists | Chart click -> Run History, cost breakdown -> Trajectory audit |
| **Mission Control** | Cost/Latency cards wired | Pipeline stages show real trace timing, service popovers with uptime/request counts |
| **Learning mode** | Summary metrics + suggestions | Run comparison (side-by-side), scatter plots, tokens-per-step distribution |
| **Audit mode** | Event log + file manifest | Before/after file diffs, PDF export, full token accounting per action |

### Acceptance criteria
1. Observability cost chart stacked by model with running total line
2. Quality panel shows AI-generated insight text
3. Clicking a chart bar navigates to that run in Run History
4. Mission Control pipeline stages display real trace timing from last run
5. Trajectory Learning mode has run comparison and efficiency charts
6. Trajectory Audit mode supports JSON + PDF export
7. All existing tests still pass + new tests for each enhancement

## Slice B: WebSocket Real-Time Subscriptions (v3)

### What it does
Replaces the 3-second polling loop with WebSocket subscriptions for live dashboard updates. SpacetimeDB natively supports WebSocket subscriptions — the client SDK already has this capability.

### Inputs / Outputs
- **Input**: SpacetimeDB WebSocket events (task status changes, agent heartbeats)
- **Output**: Instant dashboard updates without polling latency

### What's net-new
- `dashboard/src/lib/spacetime.ts` refactored from HTTP polling to WebSocket subscription
- Dashboard components receive push updates instead of polling
- Fallback to polling if WebSocket connection fails
- Connection status indicator in sidebar footer

### What breaks if this goes wrong
- Dashboard stops receiving live data if WebSocket connection drops without fallback
- SpacetimeDB server must support WebSocket protocol (it does natively)

### Acceptance criteria
1. Dashboard receives task/agent updates within 100ms of SpacetimeDB change
2. Automatic reconnection with exponential backoff
3. Graceful fallback to 3s polling if WebSocket unavailable
4. Connection indicator shows WebSocket vs polling mode
5. No increase in SpacetimeDB server load

## Slice C: Discord Integration

### What it does
Wires JustAi orchestrator events into Discord channels. Users can trigger runs from Discord, receive status updates, and view summaries.

### Inputs / Outputs
- **Input**: Discord commands (!justai run "goal", !justai status)
- **Output**: Discord messages with run progress, completion summaries, failure alerts

### What's net-new
- `justai/discord.py` — Discord bot module using discord.py
- Webhook integration for push notifications (no bot required for receive-only)
- Discord slash commands for interactive control
- Event hooks in orchestrator.py to emit Discord notifications at each pipeline stage

### What breaks if this goes wrong
- Discord bot token misconfigured = silent failure (must not block orchestrator)
- Rate limiting on Discord API (respect 50 req/s)

### Acceptance criteria
1. `!justai run "goal"` triggers a pipeline from Discord
2. Pipeline stage transitions post status messages
3. Run completion posts summary with cost/duration/status
4. Failures post alert with root cause from AI analysis
5. Works with webhook-only mode (no bot token required)
6. All Discord calls are async and non-blocking to the pipeline

## Slice D: Agent Payment Ledger

### What it does
Tracks cost attribution per agent, per run, per model. Every LLM call logs its cost to a ledger. Dashboard surfaces spend by agent, budget alerts, cost trends.

### Inputs / Outputs
- **Input**: LangFuse trace cost data + agent assignment from delegator
- **Output**: Per-agent cost ledger, budget thresholds, cost dashboard panel

### What's net-new
- `justai/ledger.py` — cost ledger module (SQLite-backed)
- Per-agent cost tracking linked to LangFuse traces
- Budget threshold configuration with alerts
- Dashboard: Agents view enhanced with cost columns, spend charts
- API: `/api/ledger/agents`, `/api/ledger/runs`, `/api/ledger/budget`

### Acceptance criteria
1. Every pipeline run records total cost attributed to assigned agent
2. `/api/ledger/agents` returns per-agent spend with daily/weekly/monthly rollups
3. Budget threshold triggers warning in Mission Control
4. Agent Registry view shows cost column and spend sparkline
5. Ledger persists across restarts (SQLite)

## Slice E: Multi-User / Authentication

### What it does
Adds user authentication to the dashboard and API. Users log in, see their own runs, and have role-based access (admin vs. operator).

### Inputs / Outputs
- **Input**: Username/password or API key
- **Output**: Authenticated sessions, per-user run isolation, role-based UI

### What's net-new
- `justai/auth.py` — authentication module (JWT tokens, bcrypt passwords)
- User management API: `/api/auth/login`, `/api/auth/register`, `/api/auth/me`
- Dashboard login page
- Session middleware on all API endpoints
- Per-user run filtering (users see only their runs)
- Admin role: sees all runs, manages users

### Acceptance criteria
1. Dashboard shows login page when not authenticated
2. API returns 401 for unauthenticated requests
3. Users see only their own runs unless admin
4. Sessions persist via JWT with configurable expiry
5. Passwords stored with bcrypt (never plaintext)
6. Single-user mode (no auth) remains available via env var

## Risks

| Risk | Mitigation |
|------|-----------|
| LangFuse SDK version changes | Pin version, wrap all calls |
| WebSocket connection instability | Automatic polling fallback |
| Discord rate limiting | Queue + backoff, webhook-only fallback |
| SQLite ledger contention under load | WAL mode, connection pooling |
| Auth token leakage | HttpOnly cookies, short expiry, refresh tokens |
